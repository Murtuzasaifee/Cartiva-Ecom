Frontend — React / Vite
Routing React Router v6, client-side. Key routes: /, /products, /cart, /orders, /support, /tickets/:id.
State Cart state via React Context (CartContext); no global store — page components fetch directly through a thin api client wrapper over fetch.
Ticket status refresh Ticket detail page polls GET /api/tickets/:id every 10s via setInterval, cancelled on unmount.
Backend — Spring Boot
REST endpoints
  • /api/products, /api/products/{id}
  • /api/customers/{id}, /orders, /tickets
  • /api/orders (POST), /api/orders/{id}
  • /api/tickets (POST), /api/tickets/{id}
  • /api/salesforce/status, /cases/{id}, /cases/retry (POST)
Scheduled jobs
  • CaseStatusPollingJob — polls Salesforce Cases modified since last run, syncs triage/resolution fields onto the matching local Ticket. Interval: cartiva.polling.interval-ms (default 10000ms), toggled by SALESFORCE_POLLING_ENABLED.
  • TicketSyncRetryJob — retries tickets that failed to push to Salesforce. Interval: cartiva.retry.interval-ms (default 60000ms).
Persistence H2 in-memory DB via Spring Data JPA repositories, seeded on startup by DataSeeder (products, demo customer, sample tickets).
Salesforce — Apex / LWC
Auth Server-to-server OAuth2 JWT Bearer flow (SalesforceCaseService), private key mounted at SALESFORCE_JWT_PRIVATE_KEY_PATH; calls Salesforce REST API v60.0.
Case triage CaseTriageService trigger-driven logic evaluates configurable priority/routing rules against incoming Cases; overrides supported via CaseTriageOverrideController.
Agent UI caseTriageDetail LWC surfaces triage results and audit trail inside the Salesforce console for support agents.
Direction Backend → Salesforce: ticket created via REST push on submit. Salesforce → Backend: Case status changes flow back through the 10s polling job (planned migration to Platform Events).
